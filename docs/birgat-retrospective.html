BiRGAT

Bidirectional Relational Graph Attention · Sentinel incident detection

A graph neural network that classifies events, not entities, as part-of-incident vs benign — so it learns the shape of an attack chain instead of memorising that a specific IP or host is “bad.” Trained on a synthetic Sentinel-like event stream, evaluated honestly, then fused with entity-behaviour channels to reach high recall at a fraction of the analyst cost.

01 · The core idea

Why events as nodes, not entities

Entity graphs (IP / host / account as nodes) push a model toward memorisation: if port 8443 appears in three incidents, the easiest rule is “8443 = malicious forever.” With events as nodes, the same port, host and account appear in thousands of benign events too, so the only signal left is the topology and timing of the chain. The design enforces this three ways: node features carry no unique identifiers (only shared-vocabulary categories), a leakage audit aborts training if any single feature nearly separates the classes, and benign traffic deliberately contains attack-shaped hard negatives.

02 · How it works

A provenance graph, sampled in both time directions

Each event is a node. Six typed, directed, time-stamped relations connect events the way the future KQL make-graph stage will: process lineage, session actions, host/user sequences, network correlation, and config-spawns-process. The model is a relational Graph Attention Network (per-relation projections and attention, temporal edge-feature bias) trained with focal loss over whole sampled subgraphs. Crucially, sampling is bidirectional: a seed event aggregates messages from its causal past and its consequences downstream.

The six relations: PROCESS_CHILD (parent→child process), SESSION_ACTION (sign-in→its actions), HOST_SEQUENCE and USER_SEQUENCE (consecutive events on a host / by an account), NET_TRIGGER (a connection→activity it triggers on the destination host), and CONFIG_TRIGGER (a registry/service change→the process it later spawns).

Anti-cheat guarantees. A leakage audit computes the single-feature AUC of every feature on the train split and aborts if any approaches 0.95 (top feature measured 0.60). A features-only MLP baseline and an edge-rewire ablation confirm the gain really comes from the graph, not from leaked features.

03 · Seeing the results

A localhost explorer for “which events flared up”

Because the point is to inspect which events the model flags, the run ships with a small stdlib-only dashboard. tools/export_predictions.py re-runs the exact training-time evaluation and joins each held-out test event with its incident metadata; tools/serve_viz.py serves it. The dashboard shows a score-vs-time timeline (flares above the threshold), per-template catch, per-incident chains with provenance edges, and a score-source switcher to compare the RGAT against each fusion operating point. Everything recomputes as you drag the threshold.

python tools/export_predictions.py runs/<run>  then  python tools/serve_viz.py  →  http://localhost:8123

04 · Honest weaknesses

The blind spots: beacon and valid-account abuse

The RGAT works, but error analysis pinned its residual misses to two deliberately-hard templates. At the precision-focused (F1) operating point, valid-account abuse is missed 93% of the time and beaconing 76%, while exploit-web and service-lateral are nearly perfect. Both hard templates overlap benign traffic by design — service accounts genuinely beacon and move gigabytes; admins genuinely use valid accounts laterally.

05 · The entity question

Does entity behaviour carry signal — without memorising?

The blind templates are distinguishable by entity-level behaviour over time (an account behaving against its own baseline, a host beaconing on a clock), which no single event can see. The fear was that an entity model just reintroduces the memorisation trap. The go/no-go tested it directly: build behavioural entity windows (cadence, fan-out, event mix, burstiness — no identity) and score every window with a model that never saw that entity. Signal generalises strongly to completely unseen entities, so it is behaviour, not identity.

06 · The hybrid

Fusing event scores with entity behaviour

Three channels feed a thin combiner: the RGAT event score, a multi-scale aggregate entity branch, and a sequence branch. The long-window aggregate (agg480) is the beacon lever; the sequence branch is the valid-account lever. Combiners are fit on validation only, never on test.

07 · Fixing valid-account

The sequence model lifts the hardest template

An earlier read claimed valid-account was an irreducible floor. That was a comparison artifact — it had compared at matched recall, where the fusion’s budget is so tight that valid-account is sacrificed first. The honest comparison is at a matched flag budget, and there the sequence branch wins: it separates valid-account from benign at AUC 0.98 (the best channel), because valid-account abuse is an ordered chain. The sequence model is a bidirectional GRU with attention pooling, trained with focal loss, so it can focus on the suspicious sub-sequence instead of averaging it away.

08 · Where it goes next

Toward real Sentinel data & automation

The model is trained on synthetic data, so real-data transfer is unproven until tested — that is the next milestone. The intended automation path is near-real-time, retrospective: when a Sentinel incident fires (alerts carry startTime/ endTime), fetch the surrounding hours of events, build the provenance graph, and score it with the trained model. Because the window is already complete, the bidirectional context is fully available — this sidesteps the “not for streaming triage” caveat in the README.

Open considerations

  • Synthetic → real transfer is unvalidated. Treat early real-data results as calibration, not production truth.
  • Real data needs labels for evaluation. Inference/demo mode needs none; metrics need incident-membership labels (keep alert rows out of features to avoid leaking the detection itself).
  • A real-data loader is the missing code half — mapping exported Sentinel tables to the schema and building the six edge relations (docs/kql_contract.md).
